# 通讯录归档与管理工具（contact-manager）说明

本文档对应后端工具包 `backend/app/tools/contact_manager/` 与前端页面 `frontend/src/views/ContactManagerView.vue`（路由 `/tools/contact-manager`）。

## 功能概述

- **项目隔离**：所有通讯录数据按「项目」划分，每个项目独立密码保护，字段定义互不影响；
- **自动表头识别与字段映射**：上传 Excel 后自动扫描前 10 行，按特征词（姓名 / 职务 / 单位 / 性别 / 电话 / 手机 / 邮箱 / 地址）打分选出最可能的表头行并给出列到字段的映射建议，可人工调整，也可把无法归类的列新建为自定义字段；
- **多版本增量归档**：每次导入生成一个「版本」（对应一个日期时点），只记录与上一版本相比有变动的联系人，未变动的数据通过回溯继承，因此可查询**任一时点的完整通讯录快照**；
- **可视化增删改查**：可基于最新版本创建新版本，对联系人做修改或删除；
- **导出与备份**：可导出任意版本为 Excel；可导出 `.cmdb`（JSON）完整数据库备份；
- **删除保护**：删除项目前必须先导出数据库备份，并再次校验密码，防止误删不可恢复。

## 数据模型

```
projects ──┬─> fields                  （每个项目独立的字段定义，UNIQUE(project_id, name)）
           ├─> contact_versions        （一次导入 = 一个版本，含 filename / sheet_name / version_date）
           └─> contact_entities        （联系人实体，以「姓名」为 entity_key，UNIQUE(project_id, entity_key)）
                    └─> contact_version_deltas  （实体在某个版本下的数据快照，is_deleted 表示逻辑删除）
```

- `contact_version_deltas` 记录的是**增量**：只有发生变化的实体才会写入一条记录，`data` 为 JSON；
- 查询某时点数据时使用 `ROW_NUMBER() OVER (PARTITION BY entity_id ORDER BY version_date DESC, id DESC)` 取每个实体在目标版本之前最近的一次变更，`is_deleted = 1` 的实体视为已删除（依赖 SQLite 3.25+ 窗口函数，实测服务器为 3.39.3）；
- 外键均为 `ON DELETE CASCADE`，删除项目会级联清除其下全部版本、实体与增量数据。

数据库文件：`backend/data/contact_manager.db`（受 `LAB_TOOLS_DATA_DIR` 控制）。**该文件不参与 TTL 自动清理**，请自行备份。

前缀 `/api/contact-manager`。除项目管理端点外，其余端点都通过
`get_project_auth` 依赖读取请求头 `X-Project-Id` / `X-Project-Password` 校验项目与密码（SHA-256 比对）。

## 字段自动识别

`parser.py` 中的 `match_row_fields` 对一行的每一列做匹配，`detect_header_and_map` 则在前 10 行内计分，选取得分最高的行作为表头：

| 字段 | 匹配关键词（部分） |
| --- | --- |
| `name` | 姓名、名字、人员姓名 |
| `title` | 职务、职称、岗位、职级 |
| `unit` | 单位、部门、工作单位、公司、机构 |
| `gender` | 性别 |
| `phone` | 电话、固定电话、办公电话、座机、联系电话 |
| `mobile` | 手机、手机号、移动电话 |
| `email` | 邮箱、电子邮箱、Email、E-mail |
| `office` | 办公地址、地址、办公地点、房间号 |

匹配优先级（每列独立判断）：

1. **与当前项目已有字段的显示名完全相同** —— 得 2 分，最可靠；
2. **命中内置特征关键词** —— 得 2 分，但**仅当该字段确实存在于当前项目**时才采用；
3. **与已有字段显示名模糊匹配** —— 得 1 分。

两个关键约束：

- **只返回当前项目真实存在的字段名**。关键词表里的 `title` 等只是「候选语义」，若项目里没有该字段就不产生映射。否则会写入一个项目里不存在的字段名，数据保存后无法展示。
- **模糊匹配要求命中词占单元格文本的 ≥ 50%**（`_CONTAINMENT_MIN_RATIO`）。否则标题行「某单位通讯录」会因为含「单位」二字被误判为单位列；而「工作单位」「单位名称」仍能正常匹配。

识别结果只是**建议**，前端会展示出来供人工确认与修改。

### 前端的映射默认值

进入映射步骤（或点击「重新自动匹配字段」、切换表头行）时，前端按下述规则为每一列给出默认值：

| 情况 | 默认值 |
| --- | --- |
| 后端匹配到已有字段 | 该字段 |
| 未匹配到，但列名非空且**已有同名字段** | 复用该字段 |
| 未匹配到，列名为空 | `__ignore__`（不导入） |
| 未匹配到，列名非空且无同名字段 | `__new__:<列名>` —— **默认按列名新建字段** |

> 注意：自动匹配依赖 `headerColumns`，因此 `fetchPreviewData` 必须先调用
> `updateHeaderColumns()` 再调用 `applyAutoMapping()`。顺序反了会让映射恒为空
> （历史缺陷）。

## 导入前的值清洗与出生年月格式化

`parse_sheet_data` 解析每一行时都会做两件事，存储的数据因此总是规范化的。

### 1. 值清理（所有字段）

移除空白与不可见噪声：全角空格 `\u3000`、不换行空格 `\u00a0`、制表/换行、零宽字符、BOM。

- `张 三`、`张\u3000三` → `张三`
- `第一行\n第二行` → `第一行第二行`
- `甲单位\r\n` → `甲单位`
- 整数型浮点 `1234.0` → `1234`

统一清理后，跨版本比较才稳定（否则多打一个空格就会被判成两个人）。

### 2. 出生年月规范化（按字段 label 判断）

字段显示名含「出生 / 生日」时，值会被解析为 **`YYYY-MM`**：

| 输入 | 结果 |
| --- | --- |
| `1968-10` / `1968/10` / `1968.10` / `1968年10月` / `196810` / `1968.10.01` | `1968-10` |
| `1968-1` / `1968年1月` | `1968-01` |
| `1968.1` | `1968-10` ← **注意** |
| `1968.01` | `1968-01` |
| Excel 日期格式的单元格（返回 datetime） | `YYYY-MM` |
| `196810` / `19681005` | `1968-10` |
| `1968`（只有年份）/ 无法识别 | 保留清理后的原值 |

**关键点**：表格常用小数录入出生年月，Excel 会把 `1968.10`（10 月）存成数值 `1968.1`
（末尾的 0 丢失），而 1 月会特意写成 `1968.01`（小数点后的 0 保留）。因此
**点号后只有一位数字时，应理解为「被截断的两位月份」**（`.1` → 10 月）。

生产数据实测：该列 324 个取值中，`.1` 出现 36 次（10 月），`.01`~`.09`、`.11`、`.12`
均为两位写法，与上述约定完全吻合，全部可正确解析。

版本日期默认从文件名中提取（支持 `20231001`、`2023-10-01`、`2023_10_01`、`2023.10.01`），提取不到时取当天日期。

## 身份标识（由后端自动计算）

联系人的唯一标识**由后端自动计算**，不再要求用户选择字段：

- **姓名**仍是识别联系人的基础：表格必须把姓名列映射到「姓名」字段，否则 `400`；
- 实体的唯一键 `entity_key` 由**后端生成**（与姓名解耦），因此**同名不同人可以各自独立存在**；
- 上一版本有、本次没有的实体 → 记为逻辑删除。

> 历史演变：早期版本把身份键硬编码为「姓名」；后改为让用户指定 `id_field`；
> 现按需求改回姓名制，并把 `id_field` 降级为不再参与逻辑的兼容列（保留避免迁移）。

### 同一次导入内重名（要求用户决定）

同份表中出现重名时，**导入会先被拦下（`409`），由用户选择处理方式**：

| 选择 | 行为 |
| --- | --- |
| **合并为一条** | 多行拼成一条：每列取第一个非空值，若有多个**不同**取值则用「、」拼接 |
| **各自保留** | 每行保留为**独立的联系人**（各自的 `entity_key` 由后端分配） |

- 未指定处理方式时，`POST /import` 返回 `409`（detail 中含重名摘要）；
- 也可先调 `POST /import/preview` 预检，返回 `duplicates` 列表、跨版本匹配预估等；
- 发生「、」拼接的字段会在响应 `merge_conflicts` 中告知，前端弹窗提示。

### 跨版本判定「同一个人」（N 字段相似度）

两个版本之间比对时，同名的人中：

> 只要某条历史记录与本条记录**除姓名外**至少 `id_match_fields` 个字段取值相同（默认 **5**，可调），
> 即认为是同一个人；否则视为新人（旧记录被标记删除）。

- 相同 = 双方均非空且相等（已清理空白后比较，`id` 等**内部键不参与比较**）；
- 多个候选时取相同字段数**最多**者，且一条历史记录只能被认领一次；
- **阈值会按本记录的可比字段数收敛**：若记录除姓名外只有 2 个非空字段，则要求这 2 个全部相同。
  否则字段少的表会因「凑不满 N 个」永远匹配不上，导致旧记录被整批误判为删除；
- 阈值存于 `projects.id_match_fields`，经 `POST /settings` 可调，`.cmdb` 导出/导入会一并携带。

## 版本覆盖与查询

### 同一日期视为同一个版本

`POST /import` 时若项目内**已存在相同 `version_date` 的版本**，会先删除旧版本再导入新数据（"覆盖"），因此同一日期永远只对应一个版本：

- 旧版本的 `contact_version_deltas` 随版本一起被删除（外键 `ON DELETE CASCADE`）；
- `contact_entities` 与字段定义**不受影响**，人员匹配依旧按上一版本进行；
- ⚠️ 该删除**严格限定在本项目内**。历史上曾在此处误加过一条不按 `project_id` 过滤的
  「清理孤儿 delta」全表语句，导致其它项目数据被清空（靠备份恢复）—— 请勿再次引入。

### 查询语义（`GET /contacts`）

| 版本归档 | 日期 | 行为 |
| --- | --- | --- |
| **选择** | （不可选） | 只在该版本内查询 |
| **不选** | 不选 | **跨版本**搜索：返回**所有版本**中匹配到的记录（带 `_version_date` 标注） |
| **不选** | 选择 | **跨版本**搜索，但只取**版本日期 ≤ 该日期**的版本 |

- 前端在选择版本后会禁用日期选择器（日期条件对单版本查询不生效）；
- 未选版本且未输关键词时，仍返回最新版本快照（或日期对应的时点快照）。

### 关键词通配符 `*`

关键词支持简单通配符，与普通包含匹配并存：

| 关键词 | 含义 |
| --- | --- |
| `张*` | 以「张」开头 |
| `*委员*` | 包含「委员」 |
| `*员` | 以「员」结尾 |
| `查*君` | 以「查」开头、以「君」结尾 |
| `张三`（不含 `*`） | 普通「包含」匹配 |

规则：`*` 匹配**任意字符序列（含空）**，其余字符按字面匹配，整串要求完全匹配（前后隐式锚定）；
`?` 等其它符号**不是**通配符，按字面处理。匹配前两侧都会先做值清理（去空白），与存储数据保持一致。

### 两次「导入前」的常规校验

| 情况 | 结果 |
| --- | --- |
| 没有任何列映射到「姓名」 | `400` 姓名列必须映射到「姓名」字段 |
| 重名且未指定处理方式 | `409` 要求用户选择合并 / 各自保留 |
| 姓名为空的行 | 跳过，响应 `skipped_count` 与 `blank_id_rows`（**原始 Excel 行号**，便于回表定位） |

## 清理空字段

工具在导入时会把「未匹配的列」自动建为新字段，若某列实际没有数据、或早期缺陷重复建了同名字段，
项目里就会积累**没有内容的字段**。管理界面提供「清理空字段」按钮（工具栏），对应接口 `GET /fields/usage` 与 `POST /fields/clean`。

### 判定「有无内容」的方式

字段数据存在 `contact_version_deltas.data` 的 JSON 里，因此必须**解析 JSON 统计**，不能只看 `fields` 表：

- `referenced`：该字段名在 JSON 中出现的次数
- `non_empty`：其中取值非空（`strip()` 后非空）的次数
- `empty = (non_empty == 0)`

`database.collect_field_usage()` 负责统计，`find_empty_fields()` 返回空字段列表。

### 删除是「无损」的

删除 `fields` 记录**不会**触碰 `contact_version_deltas` 里的任何数据 —— 只是该字段不再出现在表格与导出中。
调用前请确认这些字段确实无内容（`find_empty_fields` 已保证）。

`POST /fields/clean` 的请求体（均可选）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `include_default` | `true` | 是否连同空的**默认字段**一起删除（如名册没有「职务」列时） |
| `field_ids` | 不传 | 只删除指定 id；不传则删除全部空字段 |
| `dry_run` | `false` | 只统计不删除 |

安全性：

- 只按 `project_id + id` 删除，**不会**误删其它项目的字段；
- `field_ids` 模式会先与「空字段集合」取交集，**有内容的字段即使被显式指定也不会删除**。

### 同名字段不再重复创建

`POST /fields` 在同显示名字段已存在时**直接复用**并返回 `reused: true`（幂等）。
历史缺陷：界面重复提交会创建多个同名字段，导入时按显示名匹配可能命中那个**空的**字段，
导致数据看似「丢失」—— 这正是之前项目里出现 13 组重名空字段的原因。

## 数据库迁移（重要）

`database.py` 的 `init_db()` 在模块导入时执行，是一个**幂等迁移**：建表、补列（如 `projects.exported_at`）、按需重建结构过时的表，并清理孤立数据。

### 必须用真实外键目标判断是否需要迁移

不要用「建表 SQL 字符串包含某子串」来判断结构是否需要迁移。曾经由此产生过一个线上故障：

1. 早期迁移用 `ALTER TABLE contact_version_deltas RENAME TO _deltas_old` 重建表；
2. SQLite 会**自动改写其它表外键里的目标表名**，于是外键一度指向 `_deltas_old`；
3. 旧代码随后 `DROP TABLE _deltas_old`，外键就变成指向已删除表的**悬空外键**；
4. 旧判断条件 `"FOREIGN KEY (version_id)" in sql` 依然成立，因此**永远不会**触发修复；
5. 连接默认 `PRAGMA foreign_keys = ON`，任何写入都报 `no such table: main._versions_old`，表现为导入接口 500。

正确做法：

- 用 `PRAGMA foreign_key_list(<表>)` 读取外键的**实际目标表**，与期望结构比对，不一致就重建；
- 重建期间设置 `PRAGMA legacy_alter_table = ON`，阻止 `RENAME` 再次改写其它表的外键引用；
- 临时表统一命名为 `_mig_<表名>`，并在迁移末尾清理历史遗留的 `_*_old` 表；
- 搬运数据时保留主键 `id`，避免破坏其它表的引用。

### 清理孤立数据的顺序

必须**先删**孤立的 `contact_versions` / `contact_entities`，**再删** `contact_version_deltas`。
顺序反了的话，delta 在这一步仍能匹配到「尚未被删掉的」孤立版本/实体，从而被漏掉。

## 安全说明

- 项目密码以 SHA-256 存储（无加盐），仅用于防止误操作与区分项目，**不是强安全边界**；整体仍应置于 ZeroTrust 之后；
- 无登录鉴权，请勿将服务直接暴露公网；
- 删除项目是级联硬删除，界面强制要求先导出 `.cmdb` 备份。
